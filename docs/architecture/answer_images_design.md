# 知识库原图展示设计总览

为控制台聊天、原生发布 API 和 OpenAI 兼容 API 提供知识库原图展示。
本文保留核心决策与交付顺序，详细契约、实现位置和测试要求放在对应模块。
测试执行入口与部署边界见 [验收指南](answer_images/08_validation.md#执行入口与部署边界)。

<a id="s1"></a>

## 目标与核心决策

用户阅读答案时，可以直接查看支撑答案的流程图、架构图、截图和图表，并追溯到原文。

第一版采用以下规则：

1. 正文按需插入原图，图片在对应说明段落之后展示；附件清单独立保存资源、来源和权限。
2. 回答引用带图片的正文片段时，服务端自动补入该片段登记的原图；按资源去重，取消两张的产品上限，未引用片段仅用于来源预览。
3. 模型只输出本轮图片引用编号，由服务端校验并解析为附件；不让模型生成或复制真实访问链接。
4. 图片展示不依赖 `supports_vision`；展示图片不意味着模型已经理解图片。
5. 所有图片与本次读取的文档版本绑定，历史消息不会换成新版本的图片。
6. 网页使用私有图片接口；公开 API 默认使用受限、可过期和撤销的图片访问链接。
7. 普通图文回答通过正文图片标记表达位置；用户只要原图时，可用选择工具直接生成纯图结果，
   不依赖文字 citation，也不为选图或展示增加独立模型调用。
8. 存储与传输解耦：默认使用受控 URL；客户端无法访问图片接口时，可显式请求受限的 `data_url` 内联传输。
9. 原始图片存储默认本地文件，可配置 S3 兼容后端（MinIO/AWS S3）；SQLite 只保存引用、定位和元数据，客户端仍访问 Nianlun。

图文回答支持模型显式引用原图，也支持服务端按回答的文字 citation 补图；模型已引用的资源不重复补入。
数量受可配置的请求资源预算约束；预算不足、来源失效或图片不可用时必须明确反馈，不静默删图。
没有有效正文 citation 或图片引用时不自动附图。补图不传递图片像素、不增加模型调用，也不推断图片内容；视觉输入是独立能力。

## 数据流与契约归属

1. 01 生成版本绑定的目录，02 只返回本次已读窗口内的可信引用。
2. 02 分配请求级逻辑编号，生成正文标记或纯图选择；不生成真实 URL。
3. 03 校验来源并归档，消息、附件、run、授权和幂等结果按约定原子完成。
4. 04 使用已提交附件解析规范正文；05 生成公开标准 Markdown，06 复用同一公开结果。

## 范围与交付顺序

<a id="s3-1"></a>

### 第一阶段：网页端可用

- 为新发布的文档建立图片目录，关联节点和字符位置。
- 提供停服执行的已有文档本地图片目录补建命令，复用已保存产物，不调用解析服务或模型。
- 检索返回可信图片引用目录，回答模型只从本轮允许集合选择，并在正文中标记展示位置。
- 支持显式发图、只发原图和基于上下文指代的发图请求，选择结果必须关联本轮重新读取的来源。
- 图片归档与会话附件持久化。
- 图片归档同时支持默认本地文件与显式配置的 S3/MinIO；首次交付即验收两种后端。
- 正文按引用顺序原位展示图片，来源面板可查看其他已成功归档的检索图片；资源复用不丢失来源。
- 图片懒加载、流式安全占位，以及完成后从附件清单解析原图链接。
- 点击放大、来源定位、加载失败和窄屏布局。
- v0/v1 共用附件选择逻辑，纯文本流程继续工作。

<a id="s3-2"></a>

### 第二阶段：发布 API 可用

- 原生 API 的可选图片清单。
- 公开图片访问链接、过期与刷新、权限撤销。
- 原生 API 显式支持 `url`/`data_url` 两种图片传输模式，默认 URL；内联模式受独立大小预算限制。
- OpenAI 兼容接口将正文图片标记原位转换为标准 Markdown 图片链接。
- 网关白名单、幂等重放和跨端验收。

两个阶段属于同一设计，但可分别验收。第一阶段完成不能宣称公开图片访问已经可用。
09 随第二阶段交付两种传输模式；控制台固定私有 URL。Data URL 只解决响应传输，不开启视觉理解。

<a id="s3-3"></a>

### 本次不包含

- 把原图发送给模型进行视觉理解。
- OCR、图片摘要、多模态 Embedding 或以图搜图。
- 用户上传图片提问、抓取外部图片、生成图片。
- 对普通文本问题额外调用独立的选图模型，以及让模型自由生成图片 URL 或访问任意外链。
- 重建全部历史文档与历史会话。

实施顺序：先确定 01/02/03/07 的类型与跨层契约，再完成目录、Agent 和归档的最小闭环，接入 04 并验收第一阶段；随后完成 05/06 并验收第二阶段。08 中的测试随对应模块同步补充。

## 设计前代码基线

现有系统已保留 MinerU 本地图片、不可变 generation/snapshot、文本检索定位、会话来源和公开 API 运行记录；尚缺回答图片目录、可信引用、历史附件与授权。已有 Markdown 渲染也需要受控附件适配，不能直接放开任意图片 URL。具体落点见各模块的计划文件表。

## 后续扩展

本设计为后续能力保留图片标识、版本、来源和归档接口，但不提前实现：

1. 视觉理解：把同一证据集合中的原图交给支持视觉的回答模型，并标记实际读取的图片。
2. 图片内容检索：入库时生成描述或 OCR，以辅助命中，回答时仍可核对原图。
3. 企业微信等渠道：复用有序图片 occurrence 和附件清单，由各渠道适配器上传媒体，
   保留图文顺序并遵循渠道数量限制，不把渠道上限反向作为网页端的统一上限。
4. 缩略图及资源预算优化：基于实际图片分布生成派生预览，原图链接仍指向原始归档字节。

以上扩展不应改变原图身份和历史版本语义，也不能把“展示过原图”当成“模型已经看过原图”。
